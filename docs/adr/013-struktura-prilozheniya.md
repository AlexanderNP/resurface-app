# ADR 013. Структура кода: модули по фичам, слои сверху вниз

Статус: принято · Дата: 2026-10-12 · Этап: 1

## Контекст
ADR 001 выбрал монолит с модулями; граница между ними держится на дисциплине. Нужна раскладка и правила импорта, чтобы на этапах 2-3 воркер и индексатор выделялись без переписывания. За основу взята методология FEOD, знакомая автору по фронтенду.

## Варианты
| Вариант | За | Против |
| --- | --- | --- |
| Модули по фичам, слои сверху вниз (FEOD под Nest) | Совпадает с feature modules Nest; границы видны в путях импорта | Правила для соседних модулей FEOD не описывает — заданы самими |
| Технические слои (`controllers/`, `services/`) | Проще начать | Код фичи размазан; выделить воркер — собирать файлы по всему дереву |
| Порты и адаптеры | Сильнейшая изоляция логики | Вдвое больше файлов там, где логики мало; нет боли, которая бы это оправдала |

## Решение
Вариант 1. Раскладка `server/src`:

```
app/          main.ts, app.module.ts — сборка
modules/      pages, saves, folders, health
common/       guard и декоратор пользователя, пайпы, фильтры
database/     подключение к базе; schema/ — все таблицы; migrations/ — одна история
```

Модуль: `index.ts` (единственная точка импорта), `*.module.ts`, `*.controller.ts`, `*.service.ts`, `*.repository.ts`, `dto/`.

Правила:
1. `app` → `modules` → `common`, `database`. Нижние слои не импортируют верхние.
2. Снаружи модуль импортируется только через `index.ts`; `exports` Nest-модуля совпадает с ним по смыслу.
3. Соседний модуль — через его `index.ts` и `imports`. Без циклов, `forwardRef` запрещён. Сейчас: `saves` → `pages`, `saves` → `folders`.
4. Граница модуля — граница транзакции: таблицы, которые меняются одной транзакцией, принадлежат одному модулю (страницы и варианты адреса — `pages`).
5. Таблицы описаны в `database/schema`, но пишет в таблицу только репозиторий модуля-владельца.
6. Подключение к базе — глобальный модуль в `database`; `app` только импортирует его.
7. Суффиксы ролей по соглашению Nest.
8. Каталог создаётся, когда в нём появляется второй файл.
9. Проверка правил 1-3 линтером отложена: [tech-debt.md](../tech-debt.md), запись 1.

Модуля пользователей на этапе 1 нет: guard и декоратор в `common`, таблица в `database/schema`.

## Последствия
- Пока нет правил линтера, нарушения границ ловит только ревью; вернуться до выделения воркера.
- Владение таблицами (правило 5) компилятор не проверяет.
- `saves` нужна транзакция, охватывающая код `pages`: способ — после пункта 4.4.
- Воркер на этапе 2 — второй корневой модуль в `app` из тех же `modules`.

## Факты
- В Nest провайдер из `providers` корневого модуля не виден импортированным модулям; нужен `@Global()` и `exports` (подтверждено в пункте 1.4).

## В продакшене я бы...
Так же, но с правилами линтера на импорты и циклы с первого дня: без них границы модулей размываются быстрее, чем их замечает ревью.

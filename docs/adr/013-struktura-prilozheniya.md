# ADR 013. Структура кода приложения: модули по фичам со слоями сверху вниз

- **Статус:** принято
- **Дата:** 2026-10-12
- **Этап:** 1

## Контекст

ADR 001 выбрал монолит с модулями и назвал цену: граница между областями держится на дисциплине, прямой импорт её ломает. Нужны раскладка каталогов и правила импорта, которые делают границы видимыми и проверяемыми, чтобы на этапах 2-3 воркер и индексатор выделялись без переписывания.

Автор пришёл из фронтенда и предложил взять за основу методологию FEOD (модули по фичам, строгое направление зависимостей сверху вниз), которую уже применял.

## Варианты

### 1. Модули по фичам со слоями сверху вниз (адаптация FEOD под Nest)

Слои `app` → `modules` → `common`, `database`. Внутри модуля: контроллер → сервис → репозиторий. Модуль доступен снаружи только через `index.ts`.

- Совпадает с тем, как Nest сам делит код (feature modules), и с опытом автора.
- Границы видны в путях импорта и проверяются линтером.
- Статья FEOD про бэкенд не описывает Nest и зависимости между соседними модулями: эти правила пришлось задать самим.

### 2. Раскладка по техническим слоям

Каталоги `controllers/`, `services/`, `repositories/` на всё приложение.

- Проще всего начать.
- Код одной фичи размазан по каталогам; границы областей не видны, выделить воркер или индексатор — значит собирать файлы по всему дереву.

### 3. Гексагональная архитектура (порты и адаптеры)

Доменный слой без зависимостей от фреймворка и базы; доступ к базе и HTTP через интерфейсы.

- Сильнее всего изолирует бизнес-логику и упрощает замену инфраструктуры.
- Удваивает число файлов и интерфейсов на этапе, где логики мало. Замера или боли, которые бы это оправдали, нет.

## Замеры и факты

- Статья `feod.dev/articles/backend.html` помечена как сгенерированная и требующая ручной доработки; примеры в ней на абстрактном фреймворке (проверено 2026-10-12).
- В Nest провайдер из `providers` корневого модуля не виден импортированным модулям. Чтобы провайдер был доступен везде, нужен модуль с `@Global()` и `exports`.
- Drizzle ведёт один журнал миграций на базу; внешние ключи проекта проходят через границы модулей (сохранение ссылается на страницу и пользователя).
- Сценарий «сохранить URL» создаёт страницу и вариант адреса в одной транзакции (requirements, раздел 4).

Замеров нет: решение о структуре кода, не о производительности.

## Решение

Вариант 1 со следующей раскладкой внутри `server/src`:

```
src/
  app/                 сборка приложения
    main.ts            точка входа
    app.module.ts      подключает database, common и модули
  modules/
    pages/             страницы, варианты адреса, нормализация адреса
    saves/             сохранения пользователя
    folders/           дерево папок
  common/              код без привязки к фиче: guard и декоратор пользователя, пайпы, фильтры
  database/            подключение к базе и описание таблиц
    schema/            все таблицы
    migrations/        одна история миграций на всю базу
```

Состав модуля (каталог появляется, когда в нём больше одного файла):

```
modules/pages/
  index.ts               единственная точка импорта модуля
  pages.module.ts
  pages.controller.ts
  pages.service.ts
  pages.repository.ts
  dto/
```

Правила:

1. **Направление зависимостей.** `app` импортирует всё; `modules` импортируют `common` и `database`; `common` и `database` не импортируют ни `modules`, ни `app`.
2. **Публичная часть модуля.** Снаружи модуль импортируется только через `index.ts`. Для внедрения зависимостей то же самое задаёт `exports` Nest-модуля: оба списка должны совпадать по смыслу.
3. **Соседние модули.** Модуль может зависеть от соседнего через его `index.ts` и `imports`. Граф зависимостей без циклов, `forwardRef` запрещён. Сейчас: `saves` → `pages`, `saves` → `folders`.
4. **Граница модуля — граница транзакции.** Таблицы, которые меняются одной транзакцией и не существуют друг без друга, принадлежат одному модулю. Поэтому страницы и варианты адреса лежат в `pages`.
5. **Владение таблицами.** Описания таблиц лежат в `database/schema`, но в таблицу пишет только репозиторий модуля-владельца. Остальные модули обращаются к владельцу через его сервис.
6. **База — нижний слой.** Подключение к базе оформлено глобальным модулем в `database`; `app` только подключает его.
7. **Имена файлов** с суффиксом роли по соглашению Nest: `pages.controller.ts`, `pages.service.ts`.
8. **Ничего заранее.** Каталоги `middlewares`, вложенные `modules`, отдельные каталоги сущностей создаются по факту появления второго файла такого рода.
9. **Проверка линтером.** Правила 1-3 закрепляются правилами линтера (запрет циклов и импортов в обход `index.ts`), а не только договорённостью.

Отдельного модуля пользователей на этапе 1 нет: guard и декоратор из ADR 012 лежат в `common`, таблица пользователей — в `database/schema`.

## Последствия

- Точка входа переезжает в `src/app`: меняются `entryFile` в `nest-cli.json` и путь в скрипте `start:prod`.
- Таблицы описаны в одном месте, поэтому владение (правило 5) компилятор не проверяет. Нарушение ловится ревью и, если получится, правилом линтера на импорты из `database/schema`.
- Сервису `saves` нужна транзакция, которая охватывает код модуля `pages`. Способ передать транзакцию через границу модуля выбирается в пункте 4.4 roadmap и дописывается сюда.
- Когда появится воркер (этап 2), он собирается вторым корневым модулем в `app` из тех же `modules`; новых слоёв для этого не нужно.
- Если бизнес-логика модуля разрастётся и начнёт зависеть от деталей базы, шаг к портам и адаптерам делается внутри одного модуля, без смены общей раскладки.

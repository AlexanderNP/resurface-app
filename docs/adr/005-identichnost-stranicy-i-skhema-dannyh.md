# ADR 005. Идентичность страницы — нормализованный адрес в таблице вариантов; схема данных этапа 1

Статус: принято · Дата: 2026-10-25 · Этап: 1

## Контекст
Одна общая страница на все записи одного адреса, личные сохранения и личное дерево папок (requirements, раздел 4). На этапе 2 у страницы появятся ещё адреса: `rel=canonical` и цель редиректа. Два одновременных сохранения одного нового адреса не должны создать две страницы. Схема: [db/schema.dbml](../db/schema.dbml), запросы: [db/queries.md](../db/queries.md).

## Варианты
| Вариант | За | Против |
| --- | --- | --- |
| Уникальный адрес в самой `pages` | Одна таблица, поиск страницы без лишнего шага | У страницы один адрес: canonical и редирект на этапе 2 потребуют склейки страниц |
| Таблица вариантов: ключ — адрес, значение — страница | Сколько угодно адресов на страницу; уникальность варианта держит база | Лишняя таблица и вставка; страница без варианта возможна, если вставки не в одной транзакции |
| Ключ — хеш адреса | Ключ фиксированной длины | Совпадение хешей склеит разные страницы; при пределе 2048 байт выигрыш не нужен |

## Решение
Таблица вариантов: первичный ключ `url_variants.url`, значение — `page_id`. Страница и её первый вариант создаются в одной транзакции (пункт 4.4); при гонке судья — первичный ключ варианта, а не проверка в коде.

Остальная схема:

| Решение | Почему |
| --- | --- |
| Сохранение — `(user_id, page_id)` первичным ключом | второе сохранение той же страницы тем же пользователем база отклонит |
| `pages.url` — адрес для показа: первый нормализованный, не меняется; `unique` | `JOIN` с вариантами дал бы строку на каждый вариант: дубли в списке и сломанная пагинация |
| Папка сохранения — `user_pages.folder_id`, `NULL` — «Входящие» | связь один ко многим хранится на стороне «многих»; у «Входящих» нет строки, охранять в коде нечего |
| Составные внешние ключи `(user_id, …)` → `folders (user_id, id)` | база не даёт положить сохранение или папку в чужую папку |
| Удаление папки: вложенные — `CASCADE`, сохранения — `SET NULL (folder_id)` | сохранения возвращаются во «Входящие»; без списка колонок обнулился бы `user_id` из первичного ключа |
| Удаление страницы с сохранениями запрещено (`RESTRICT`) | страница общая: каскад стёр бы сохранения других пользователей |
| `UNIQUE NULLS NOT DISTINCT (user_id, parent_id, name)` | одноимённые папки рядом запрещены, в том числе в корне, где `parent_id` — `NULL` |
| Адрес не длиннее 2048 байт (`check_bytes_length`) | предел записи B-tree индекса около 2700 байт; длиннее — ошибка базы вместо отказа на входе |
| `pages.id` — `bigint generated always as identity`; пользователи и папки — `uuid` | `page_id` лежит в самых больших таблицах и их индексах: 8 байт вместо 16, вставка в правый край B-дерева; `uuid` уходят клиенту, их нельзя угадать перебором |
| Колонки следующих этапов не создаются | форма колонки известна только вместе с кодом, который её пишет (состояние страницы — этап 2) |

Индексы сверх ключей и уникальных ограничений:

| Индекс | Запрос | Почему |
| --- | --- | --- |
| `user_pages (user_id, saved_at, page_id)` | список сохранений с keyset-пагинацией (4.7) | частый запрос; `LIMIT` берёт 20 строк из тысяч сохранений пользователя |

Не создаётся `user_pages (user_id, folder_id)` для `SET NULL` при удалении папки (5.4): первичный ключ `(user_id, page_id)` сужает поиск до сохранений одного пользователя, удаление папки редкое, а индекс обновлялся бы при каждом сохранении и переносе. Остальные запросы покрыты первичными ключами и уникальными ограничениями: [db/queries.md](../db/queries.md).

## Последствия
- Гонку двух сохранений одного адреса решает база; код обрабатывает конфликт уникальности (4.4, проверка — 4.5).
- Поиск страницы по адресу — один поиск по первичному ключу варианта; все вставки проверяют внешние ключи по уже существующим индексам.
- Удаление папки перебирает сохранения пользователя. Индекс `(user_id, folder_id)` вернуть, если у списка сохранений появится фильтр по папке или «Входящим» (контракт 4.1) или замер на этапе 5 покажет медленное удаление.
- `ON DELETE SET NULL (folder_id)` и `NULLS NOT DISTINCT` не выражаются в DBML: проверить в `migration.sql` пункта 2.2.
- Запрет циклов в дереве — в коде (ADR 011), внешний ключ его не ловит.

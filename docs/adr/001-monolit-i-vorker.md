# ADR 001. Монолит с модулями, воркер позже отдельным процессом

Статус: принято · Дата: 2026-10-11 · Этап: 1

## Контекст
Один автор, 4-5 часов в неделю. Пик по расчёту — около 14 запросов в секунду (requirements, раздел 3). Сохранение URL меняет три таблицы и должно быть атомарным. На этапе 2 появятся походы на чужие сайты.

## Варианты
| Вариант | За | Против |
| --- | --- | --- |
| Монолит с модулями; воркер — второй процесс из того же кода | Одна транзакция на сохранение; вызов между областями — вызов функции; одна сборка и CI | Границы модулей держатся на дисциплине |
| Микросервисы с первого дня | Независимый деплой и масштабирование | Нет общей транзакции; нужны таймауты, повторы, идемпотентность уже на этапе 1; сетевые вызовы съедают бюджет p95 < 300 мс |
| Один процесс навсегда, воркер внутри API | Проще всего запустить | Походы на чужие сайты конкурируют с API за процесс; API и воркер нельзя масштабировать раздельно |

## Решение
Монолит на Nest с модулями и одной базой Postgres. Воркер — второй процесс из того же кода на этапе 2. Сервис выделяется только после замера и отдельного ADR; первый кандидат — индексатор.

## Последствия
- Границы модулей с первого дня (ADR 013), иначе выделение воркера станет переписыванием.
- Приложение без состояния в памяти и на диске, чтобы на этапе 8 работать в нескольких экземплярах.
- Проблемы распределённых систем приходят по одной: очередь на этапе 2, второе хранилище на этапе 3.
- Части нельзя выкатывать независимо.

## Факты
Проверка двух экземпляров на одной базе — после пункта 6.4.

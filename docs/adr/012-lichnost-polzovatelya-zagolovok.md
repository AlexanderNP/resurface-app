# ADR 012. Личность пользователя на этапе 1: заголовок `X-User-Id`

- **Статус:** принято
- **Дата:** 2026-10-11
- **Этап:** 1

## Контекст

`user_id` присутствует в таблицах с первого дня (requirements, раздел 2). Целевая схема безопасности: шлюз проверяет JWT и передаёт внутрь заголовок с идентификатором пользователя, API этому заголовку доверяет (requirements, раздел 7). Шлюза на этапе 1 нет.

Нужно решить, откуда API берёт идентификатор пользователя до появления шлюза.

## Варианты

### 1. Заголовок `X-User-Id` и guard

Guard читает заголовок, проверяет формат и передаёт пользователя в обработчик. Тестовые пользователи создаются в базе заранее.

- Совпадает с целевым контрактом: при появлении шлюза внутри API ничего не меняется.
- В тестах можно выступать от имени разных пользователей и проверять, что они не видят чужие данные.
- Любой, кто может отправить запрос в API, может назваться любым пользователем.

### 2. Один идентификатор, зашитый в код

- Не требует кода.
- Нельзя проверить изоляцию данных двух пользователей.
- При появлении шлюза придётся менять все места, где используется идентификатор.

### 3. Настоящая аутентификация по JWT внутри API

- Ближе к готовому продукту.
- Не относится к теме этапа; по целевой схеме проверка токена живёт в шлюзе, поэтому работу придётся переносить.

## Замеры и факты

- На этапе 1 API запускается только локально и в CI, наружу не открыт.
- Риск подделки `userId` при доступе в обход шлюза уже записан в requirements, раздел 7; усиление отнесено к отдельному этапу.

## Решение

Вариант 1: заголовок `X-User-Id`, guard и декоратор параметра. Запрос без заголовка или с заголовком неверного формата получает 401.

## Последствия

- API нельзя открывать наружу, пока перед ним нет шлюза.
- Приложение не хранит сессий: личность приходит с каждым запросом, что нужно для запуска в нескольких экземплярах.
- Идентификатор пользователя попадает в код только через один декоратор. Смена источника (шлюз, подписанный внутренний токен) затронет один guard.

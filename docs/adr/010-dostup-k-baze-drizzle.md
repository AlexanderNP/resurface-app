# ADR 010. Доступ к базе через Drizzle ORM (ветка 1.0.0-rc), свой провайдер Nest

Статус: принято · Дата: 2026-10-11, пересмотрено 2026-10-18 · Этап: 1

## Контекст
Нужны схема, миграции и запросы к Postgres. Этап 1: уникальные ограничения, `INSERT ... ON CONFLICT`, явные транзакции, обход дерева. Этапы 2-3: блокировки строк, outbox. Автор должен видеть SQL и границы транзакций.

## Варианты
| Вариант | За | Против |
| --- | --- | --- |
| Drizzle ORM | Запросы близки к SQL и типизированы; миграции — читаемые SQL-файлы | Новый для автора; стабильная `1.0` ещё не вышла |
| Prisma | Опыт автора, хорошая типизация | Свой язык схемы; рекурсия и блокировки — сырым SQL |
| TypeORM | Зрелый `@nestjs/typeorm` | Сильнее всего прячет SQL и границы транзакций |

Подключение к Nest: официальный `@nestjs/drizzle` (версия `0.0.1` от 2026-09-23) или свой провайдер.

## Решение
Drizzle и `drizzle-kit` ветки `1.0.0-rc`: на неё рассчитаны примеры в документации Drizzle и Nest. Точные версии — в `server/package.json`. Подключение — свой провайдер (учебное решение: тренировка внедрения зависимостей).

Устройство (`server/src/database`):
- `PG_POOL` — фабрика создаёт пул `pg`: до 20 соединений, простаивающее закрывается через 30 с, ожидание соединения — не больше 2 с.
- `DRIZZLE` — экземпляр Drizzle поверх пула. Наружу модуль отдаёт только его, внедрение через `@InjectDrizzle()`.
- Модуль глобальный (ADR 013, правило 6).
- Без базы приложение не стартует: `onModuleInit` выполняет проверочный запрос.
- Пул закрывается в `onApplicationShutdown`, то есть после закрытия HTTP-соединений, поэтому запросы, которые ещё выполняются, не получают «пул закрыт». В `main.ts` включён `enableShutdownHooks()`.
- У пула есть обработчик `error`, пишет в лог Nest. Без него разрыв простаивающего соединения со стороны базы роняет процесс.

`GET /health` (`server/src/modules/health`, `@nestjs/terminus`): `select 1` с ограничением 1 с, ответ 200 или 503.

## Последствия
- `rc` может менять API до `1.0`; `^1.0.0-rc.4` пропускает следующие `rc`. Обновление — отдельной задачей с прогоном сборки и тестов.
- Запросы этапов 2-3 остаются типизированными и видимыми в коде.
- Переход на стабильную `1.0` — отдельной задачей после её выхода.

## Факты
Проверка 2026-10-18:

| Сценарий | Результат |
| --- | --- |
| База работает | 200 за 15 мс |
| База остановлена после старта приложения | 503 за 9 мс, приложение живо |
| База снова запущена | 200 без перезапуска приложения |
| Приложение остановлено | соединений приложения в `pg_stat_activity` нет |
| Без обработчика `error` у пула, база остановлена | процесс приложения упал, `curl` не смог подключиться |

## В продакшене я бы...
Взял бы официальный модуль интеграции или стабильную ветку ORM, а свой провайдер — только если модуль незрелый. Пул и таймауты подбирал бы замером под число экземпляров и лимит соединений Postgres (`max_connections`).

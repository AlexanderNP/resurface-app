# ADR 010. Доступ к базе через Drizzle ORM

- **Статус:** принято
- **Дата:** 2026-10-11, пересмотрено 2026-10-18
- **Этап:** 1

## Контекст

Приложению на Nest.js нужен способ описывать схему Postgres, менять её миграциями и выполнять запросы. От базы проекту понадобятся:

- на этапе 1: уникальные ограничения, вставка «создай или верни существующее» (`INSERT ... ON CONFLICT`), явные транзакции, обход дерева папок;
- на этапах 2-3: блокировки строк, атомарная вставка записи «обрабатывается», таблица outbox.

Цель проекта учебная: автор должен видеть, какой SQL уходит в базу и где проходят границы транзакций.

## Варианты

### 1. Drizzle ORM

- Запросы пишутся вызовами TypeScript, близкими к SQL, с проверкой типов.
- Миграции — SQL-файлы, которые генерируются из схемы и читаются глазами.
- Автор с ним раньше не работал.

### 2. Prisma

- У автора есть опыт на прошлом проекте; хорошая документация и типизация.
- Свой язык описания схемы.
- Рекурсивные запросы и блокировки строк пишутся сырым SQL в обход основного интерфейса.

### 3. TypeORM

- Привычный для Nest, есть зрелый модуль `@nestjs/typeorm`.
- Сильнее всего прячет SQL: какие запросы реально выполняются и где транзакция, видно хуже.

## Замеры и факты

Проверено 2026-10-11 и 2026-10-18:

- Документация Drizzle (`orm.drizzle.team/docs/get-started-postgresql`) по умолчанию устанавливает ветку `rc`: `drizzle-orm@rc`, `drizzle-kit@rc`.
- Документация Nest (`docs.nestjs.com/data/drizzle`) тоже предлагает `drizzle-orm@rc`.
- Официальный модуль `@nestjs/drizzle` существует в единственной версии `0.0.1` (2026-09-23).

Замеров производительности нет: вариант выбирался не по скорости.

## Решение

Drizzle ORM ветки `1.0.0-rc` вместе с `drizzle-kit` той же ветки. Точные версии фиксирует `server/package.json`.

Ветка `rc` выбрана вместо стабильной `0.45.x`, потому что на неё рассчитаны примеры в документации Drizzle и Nest. Стабильная ветка потребовала бы сверять каждый пример со старой документацией.

## Последствия

- Время на освоение нового инструмента в начале этапа.
- Запросы этапов 2-3 остаются типизированными и видимыми в коде.
- Ветка `rc` может менять API до выхода `1.0`. Диапазон `^1.0.0-rc.4` пропускает следующие `rc` и `1.0.0` при `npm install` без `package-lock.json`. Обновления выполнять отдельной задачей, проверяя сборку и тесты.
- После выхода стабильной `1.0` перейти на неё отдельной задачей.

## Способ подключения к Nest

Свой провайдер вместо `@nestjs/drizzle`: модуль версии `0.0.1` не нужен, а свой провайдер — это тренировка внедрения зависимостей (решение автора, пункт 1.4).

Код лежит в `server/src/database`:

- Фабричный провайдер под токеном `PG_POOL` создаёт пул `pg` из конфигурации `database`. Параметры: до 20 соединений; простаивающее соединение закрывается через 30 с; ожидание соединения ограничено 2 с, после чего запрос завершается ошибкой, а не зависает.
- Провайдер `DRIZZLE` получает пул и создаёт экземпляр Drizzle. Наружу модуль экспортирует только `DRIZZLE`, поэтому у модулей приложения один путь к базе. Внедрение — через декоратор `@InjectDrizzle()`.
- Модуль глобальный (`@Global()`) по правилу 6 ADR 013; `app` только импортирует его.
- **Старт без базы невозможен:** в `onModuleInit` модуль берёт соединение, выполняет проверочный запрос и возвращает соединение в пул. Без базы приложение не поднимается.
- **Закрытие:** пул закрывается в `onApplicationShutdown`. Этот хук вызывается после того, как закрыты HTTP-соединения, поэтому запросы, которые ещё выполняются, не получают ошибку «пул закрыт». В `main.ts` включён `enableShutdownHooks()`: без него сигнал остановки хуки не вызывает.

- **Ошибки простаивающих соединений:** у пула есть обработчик события `error`, который пишет ошибку в лог Nest. Без обработчика разрыв соединения со стороны базы (остановка, перезапуск) ронял процесс приложения: проверка 2026-10-18 вместо 503 получила отказ в соединении с приложением.

`GET /health` (`server/src/modules/health`) построен на `@nestjs/terminus`: выполняет `select 1` с ограничением 1 с, отвечает 200 или 503.

Проверка 2026-10-18 (критерии пункта 1.4):

| Сценарий | Результат |
| --- | --- |
| База работает | 200 за 15 мс |
| База остановлена после старта приложения | 503 за 9 мс, приложение работает дальше |
| База снова запущена | 200 без перезапуска приложения: пул открыл новое соединение |
| Приложение остановлено | соединений приложения в `pg_stat_activity` не осталось |

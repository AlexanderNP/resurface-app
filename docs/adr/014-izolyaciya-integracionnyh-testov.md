# ADR 014. Интеграционные тесты на Postgres с очисткой между тестами

Статус: принято · Дата: 2026-11-19 · Этап: 1

## Контекст

Тесты должны проверять ограничения и транзакции настоящего Postgres. В пункте 4.5 параллельные запросы работают через разные соединения и фиксируют изменения. Эти данные нужно убирать перед следующим тестом.

## Варианты

| Вариант | За | Против |
| --- | --- | --- |
| Отдельная база в Compose | Можно использовать имеющийся Postgres | Перед запуском нужно поднять Compose и правильно выбрать тестовую базу |
| Контейнер на прогон, очистка перед каждым тестом | Тесты сами создают временную базу. Можно проверять реальные коммиты | Тесты, которые делят базу и очищают её, идут последовательно |
| Транзакция с откатом на тест | Изменения внутри транзакции удаляются одним откатом | Откат не уберёт коммиты, выполненные через другие соединения |

## Решение

`make test-int` из `server/` запускает Vitest. Testcontainers поднимает `postgres:17` на прогон, а `globalSetup` применяет миграции. Перед каждым тестом `TRUNCATE … RESTART IDENTITY` очищает таблицы из схемы Drizzle, затем `seedUsers` создаёт двух известных пользователей. Vitest запускает файлы по очереди.

## Последствия

- Тест на гонку может открывать параллельные транзакции внутри одного тестового сценария.
- Журнал миграций сохраняется между тестами. Новый прогон получает новый контейнер.
- Длительность прогона растёт с числом тестов. Если замеры покажут, что последовательный запуск замедляет обратную связь, можно дать каждому воркеру свою базу.

## Факты

- 2026-11-19 — без вызова очистки второй тест нашёл страницу из первого. С включённой очисткой `make test-int` дал `2 passed` в трёх прогонах подряд.

## В продакшене я бы...

В CI проверял бы ограничения на той же основной версии PostgreSQL, что и в продакшене. При измеренной необходимости ускорить тесты выделил бы отдельную базу каждому воркеру.

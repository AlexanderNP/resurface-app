# Словарь терминов проекта

## ADR (Architecture Decision Record)

Короткая запись одного архитектурного решения: контекст, рассмотренные варианты, принятое решение и его последствия. Пишется в момент решения, чтобы через время можно было понять, почему сделано именно так. В этом проекте каждая запись заканчивается строкой «в продакшене я бы...». Записи лежат в `docs/adr/`.

## Процесс

Запущенная программа со своей отдельной памятью. Команда `node dist/main.js` в терминале создаёт один процесс; та же команда во втором терминале создаёт второй, и переменные у них не общие.

## Сервис

Программа с одной ролью, к которой обращаются по сети: API, Postgres, RabbitMQ. Слово отвечает на вопрос «что это делает», а не «где это запущено».

## Экземпляр (инстанс)

Одна запущенная копия сервиса, то есть один его процесс. Один сервис может работать в нескольких экземплярах на одной или на разных машинах.

## Контейнер

Изолированная «коробка» для процесса со всем, что ему нужно для запуска (Docker). На одной машине помещается много контейнеров.

## Сервис без состояния (stateless)

Сервис, экземпляры которого ничего не помнят о клиенте между запросами: всё, что должно пережить запрос, лежит снаружи (база, брокер, токен у клиента). Только такой сервис можно запускать в нескольких экземплярах за балансировщиком.

## ORM

Библиотека, которая позволяет работать с таблицами базы через объекты и методы языка программирования вместо строк SQL.

## Миграция

Файл с одним изменением схемы базы (создать таблицу, добавить ограничение). Хранится в git и применяется по порядку, поэтому схема у всех одинаковая и её историю видно.

## Уникальное ограничение

Правило в самой базе: в колонке (или наборе колонок) не может быть двух одинаковых значений. База откажет во вставке дубликата, даже если два запроса пришли одновременно.

## Транзакция

Группа изменений в базе, которая выполняется целиком или не выполняется вовсе. Если посередине случился сбой, база откатывает уже сделанное.

## Гонка (race condition)

Ошибка, которая возникает, когда два запроса работают одновременно и результат зависит от того, кто успел раньше. Пример: оба проверили, что страницы нет, и оба её создали.

## Нормализация адреса

Приведение разных записей одного адреса к одной форме (схема, `www`, регистр домена, трекинговые параметры), чтобы одна страница не хранилась несколько раз. Правила: requirements, раздел 4.

## Вариант адреса

Одна из записей адреса, ведущих на ту же страницу. Таблица вариантов связывает каждый вариант ровно с одной страницей.

## Список смежности (adjacency list)

Способ хранить дерево в таблице: у каждой строки есть ссылка на родителя (`parent_id`). Как в файловой системе: папка знает только, в чём она лежит.

## Рекурсивный запрос (recursive CTE)

Запрос Postgres, который идёт по ссылкам «родитель — потомок» шаг за шагом, пока они не кончатся. Позволяет одним запросом получить всю ветку дерева или путь до корня.

## Guard

Класс Nest, который выполняется до обработчика запроса и решает, пропустить запрос или отклонить. В проекте достаёт идентификатор пользователя из заголовка.

## Интеграционный тест

Тест, который проверяет код вместе с настоящей зависимостью (здесь — с настоящим Postgres в контейнере), а не с её подделкой.

## CI (непрерывная интеграция)

Автоматический прогон линтера, тестов и сборки на каждое изменение в репозитории. В проекте — GitHub Actions.

## Слой

Группа кода с одной ролью и правилом, от кого она может зависеть. В проекте: `app` → `modules` → `common` и `database`; зависимости идут только сверху вниз.

## Публичная часть модуля

То, что модуль разрешает использовать снаружи. В проекте это содержимое его `index.ts` и список `exports` Nest-модуля; всё остальное — внутреннее устройство, которое можно менять, не трогая соседей.

## Циклическая зависимость

Ситуация, когда модуль A зависит от B, а B от A (напрямую или через цепочку). Такие модули нельзя ни понять, ни выделить по отдельности.

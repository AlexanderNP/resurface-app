# Требования: сервис личной библиотеки ресурсов

## 1. Цель проекта

**Цель:** получить навыки System Design на практике, строя полезный для себя продукт. Проект закрывает техническую часть пути к роли Tech Lead full-stack инженера: проектирование систем, backend и DevOps. Навыки ревью, оценки задач и командной коммуникации проектом не закрываются и развиваются отдельно, на работе.

Каждое значимое решение сопровождается замером и записью ADR, чтобы его можно было объяснить.

### Принципы проекта

1. **Развитие от боли.** Начинаем с простого приложения. Сложность (кэш, отдельный сервис, шардирование) добавляется только после замера, который показал проблему, и записи в ADR.
2. **Обучение важнее продукта.** Если лучшее для продукта решение лишает учебной боли, берётся учебное. Каждое такое решение явно помечается в ADR.
3. **ADR на каждое значимое решение.** Контекст, варианты, решение, последствия и обязательная строка: «В продакшене на реальном масштабе я бы...».
4. **Учёба перед этапом.** Перед каждым этапом читается/смотрится тема из System Design Primer или ByteByteGo (30-60 минут), затем делается реализация, замер и ADR.
5. **Код пишет автор.** Ассистент ведёт обсуждение, план и ревью.

### Ограничения

- Время: 4-5 часов в неделю.
- Ориентировочная длительность 8 этапов: 8-12 месяцев. Первая жертва при нехватке времени: этапы 7-8.
- Стек: Nest.js, TypeScript, Postgres, RabbitMQ, OpenSearch, Redis (после замеров), Vue 3 / Vite / vite-plugin-pwa, Docker.

## 2. Продукт

### Проблема

Ресурсы, найденные при изучении технологий, складываются в чат «Избранное» мессенджера. Позже их невозможно найти, и нет повода открыть, потому что фокус сменился на другую технологию.

### Пользователи

В первой версии единственный пользователь — сам автор. Нагрузка синтетическая (генерируется скриптами). Многопользовательский и публичный режим возможны в будущем, поэтому `user_id` присутствует в таблицах с первого дня.

### Ключевые сценарии

1. **Захват.** Автор читает статью и в один клик из расширения браузера добавляет её. Необязательное поле «зачем» (одна короткая фраза). Больше действий при захвате нет.
2. **Поиск.** Через неделю автор знает, что задача решается «какой-то коллекцией». Он находит статью по слову или по дереву «Программирование → Python → Коллекции».
3. **Контекстный возврат** — показ связанных сохранённых ресурсов, пока ты читаешь другую страницу. Автор открыл статью, нажал на иконку расширения и видит категорию статьи и список ресурсов из своей библиотеки на ту же тему (по ключевым словам и тегам). Так сохранённое не лежит мёртвым грузом, а само попадается на глаза, когда оно нужно. Это основной антихлам-механизм.

### Функциональные требования v1

- Добавление страницы по URL из расширения; поле «зачем» необязательное.
- Новое сохранение попадает в папку «Входящие». Система предлагает папку из дерева пользователя по ключевым словам; пользователь принимает одним кликом или игнорирует. Папки создаёт только пользователь.
- Дерево папок (личное), теги (личные), заметка «зачем» (личная).
- Полнотекстовый поиск по словам внутри страниц; ограничен только страницами этого пользователя. Сортировка и пагинация.
- Расширение: на странице показывает категорию и связанные сохранённые ресурсы. Запрос уходит по клику на иконку. Автоматический режим на выбранных доменах включается в настройках (приватность).
- Статус обработки страницы виден в списке и в расширении (тихий, без уведомления о каждом успехе).
- Если сайт не отдал страницу и все автоматические попытки исчерпаны, страница получает состояние «недоступно». В интерфейсе рядом с ней есть кнопка «Повторить»: пользователь может сам запустить получение страницы заново, например после того как сайт снова заработал.

### Поведение расширения на неизвестной странице

Расширение показывает индикатор «анализируем». Сервер ставит задачу получения страницы с повышенным приоритетом. Если страница доступна анониму, результат появляется за целевое время; повторный клик на ней мгновенный. Если страница недоступна анониму: «страница закрыта, связанное недоступно», повторные попытки не выполняются.

### Ограничения продукта (осознанные)

- Контекстный возврат (показ связанных сохранённых ресурсов на странице, которую пользователь читает, см. сценарий 3) работает только в браузере с установленным расширением, то есть на десктопе. На мобильных устройствах он недоступен, потому что большинство мобильных браузеров не поддерживают расширения.
- Расширение не присылает на сервер текст открытой страницы: за содержимое страницы всегда ходит сам сервер. Причины. Во-первых, текст общий для всех пользователей, и злонамеренный пользователь мог бы подменить его для других. Во-вторых, расширение видит страницы за логином (внутренняя вики, закрытые документы), и их текст не должен попасть в общую часть и стать видимым другим.
- Содержимое общей страницы определяется тем, что видит анонимный сервер. Закрытые страницы (за логином, платной стеной, на JavaScript) сохраняются только в личной части без текста и ключевых слов.

### Вне первой версии

Мобильное приложение и добавление с мобильного (после расширения: веб-сервис с PWA), текст страницы от расширения, смысловой поиск (эмбеддинги), совместный доступ, оплата, импорт из «Избранного», напоминания по дате.

## 3. Нефункциональные требования

### Допущения и расчёты

Все допущения консервативны и взяты из поведения автора в дни активной учёбы.

| Параметр | Значение | Обоснование |
| --- | --- | --- |
| Зарегистрированных пользователей | 100 000 | базовая точка расчёта |
| Доля DAU | 30% (30 000) | верхняя оценка для утилиты, используемой по необходимости |
| Сохранений на DAU в день | 3 | поведение автора |
| Кликов по иконке на DAU в день | 10 | поведение автора |
| Сохранений в день | 90 000 | 30 000 × 3 |
| Кликов в день | 300 000 | 30 000 × 10 |
| Среднее RPS сохранений | ≈ 1 | 90 000 / 86 400 |
| Среднее RPS кликов | ≈ 3,5 | 300 000 / 86 400 |
| Коэффициент пика | 4 | основная активность в вечерние часы, часовые пояса сглаживают |
| Пиковое RPS сохранений | ≈ 4 | |
| Пиковое RPS кликов | ≈ 14 | |
| Записей сохранений в год | ≈ 32,85 млн | 90 000 × 365 |
| Метаданные в год | ≈ 13 ГБ | ≈ 400 байт на запись, без учёта дедупликации и индексов |
| Текст целиком без дедупликации | ≈ 295 ГБ в год | ≈ 9 КБ на запись; от хранения отказались |

Вывод: при расчётных 14 RPS один Postgres справляется без кэша. Обоснование усложнения не в RPS, а в:
- внешнем I/O (задержка и ненадёжность чужих сайтов) → очередь;
- требовании к задержке отклика расширения;
- учебной цели проекта.

### Целевой масштаб

Определяется нагрузочным тестом простой версии: найти RPS, при котором она ломается, и поставить цель выше (например, 3×). Число «1 млн пользователей» произвольным не фиксируется.

### Целевые задержки (проверяются замером)

- Клик по иконке на известной странице: p95 < 300 мс.
- Подтверждение сохранения: p95 < 300 мс.
- От сохранения до появления в поиске (страница доступна анониму): p95 < 30 с.

### Прочее

- Доступность, число инстансов, RPO/RTO: определить на этапах 7-8.
- Дедупликация текста: одна страница хранится один раз независимо от числа сохранивших.

## 4. Данные и идентичность

### Общее и личное

- **Общая страница:** URL (идентичность), заголовок из серверного похода, текст/индекс, ключевые слова, автокатегория, состояние обработки.
- **Личное сохранение:** связь пользователя со страницей, заметка «зачем», теги, папка в дереве, дата сохранения.
- **Таблица вариантов адреса:** ключ — вариант адреса (уникален на уровне базы данных), значение — страница. Один вариант не может принадлежать двум страницам.
- Заголовок из вкладки браузера личный (иначе название приватного документа утекает другим пользователям).

### Правила нормализации адреса (консервативные)

Принцип: ошибаться в сторону дубликата, а не склейки двух разных страниц (склейка разрушает данные).

- Схема (`http`/`https`) и `www` приводятся к одной форме.
- Завершающий слэш: одно правило на весь проект.
- Регистр: приводится только домен. Путь не приводится (он регистрозависим).
- Параметры: удаляются только известные трекинговые (чёрный список): `utm_*`, `gclid`, `fbclid`, `yclid`, `msclkid`, `ttclid`. Остальные сохраняются (`?v=` у видео, `?id=` и т. п.). `ref` в список не входит (двусмысленный).
- Тег `rel=canonical` страницы читается после похода; расхождение с предварительным адресом фиксируется в таблице вариантов.

### Поиск

- Postgres — источник правды. OpenSearch — производный индекс: одна запись на страницу.
- Фильтр «только страницы пользователя» применяется при запросе. Способ выбирается замером.
- Индекс догоняет базу (eventual consistency). Синхронизация через transactional outbox.

## 5. Конвейер обработки страницы

### Состояния общей страницы

1. В очереди.
2. Обрабатывается (с меткой времени начала работы).
3. Готово.
4. Ждёт повтор (номер попытки, время следующей попытки).
5. Недоступно.

Состояния взаимоисключающие. Записать противоречивую комбинацию (например, «готово» и «ошибка») невозможно.

### Правила

- `404` и `403` → сразу «недоступно» (повтор бессмыслен).
- `503`, `429` и сетевые сбои → «ждёт повтор».
- Повторы: паузы 1 мин, 5 мин, 30 мин, 6 ч; предел 4 попытки; затем «недоступно» и возможность ручного повтора.
- Зависшая задача: аренда (lease) на стороне брокера/воркера, отсчёт от взятия в работу. Клиент таймаутом не владеет. Падение воркера не показывается пользователю как ошибка.
- Идемпотентность: воркер атомарно пытается вставить запись «обрабатывается» (уникальность в базе). Проигравший читает состояние: «готово» → пропустить; «обрабатывается, свежая метка» → выйти; «обрабатывается, метка протухла» → забрать.
- Обновление известных страниц: периодическая фоновая задача; стратегия (по популярности, условные запросы, хеш содержимого) определяется на этапе 2.

## 6. Архитектура

- Начало: одно приложение на Nest.js (модули внутри) и воркер отдельным процессом из того же кода.
- Брокер: RabbitMQ.
- Выделение сервисов только по замеру и ADR. Первый кандидат: индексатор.

### Клиенты

- Расширение браузера (Manifest V3; интерфейс на Vue) — первый.
- Веб-сервис и PWA на Vue 3 / Vite / vite-plugin-pwa — второй. Мобильное добавление через PWA после появления веб-сервиса. Проверить поддержку Web Share Target на iOS.

## 7. Безопасность

- JWT проверяется на шлюзе. Внутренние сервисы доверяют заголовку `userId`. Наружу открыт только шлюз. Риск: подделка `userId` при доступе в обход шлюза. Усиление (подпись внутреннего токена, сетевая изоляция) на отдельном этапе.
- SSRF: краулер запрещает приватные и локальные адреса, ограничивает размер и время ответа, уважает `robots.txt`, использует собственный `User-Agent`, ограничивает запросы на домен.
- Rate limiting на публичных эндпоинтах.
- Секреты: Docker secrets.
- Логи и метрики не должны содержать URL приватных страниц в открытом виде (проверить на этапе наблюдаемости).

## 8. Инфраструктура, наблюдаемость, тестирование

- Разработка: Docker Compose. Позже: Docker Swarm, затем Kubernetes.
- CI: GitHub Actions (линтер, тесты, сборка образа).
- Логи: структурированные, со сквозным идентификатором запроса. Метрики: Prometheus + Grafana. Трассировка: OpenTelemetry (позже). Проверки здоровья.
- Тесты: unit и интеграционные на настоящих Postgres и RabbitMQ в контейнерах.
- Нагрузка: k6, поиск точки излома.
- Хаос: остановка воркера, остановка брокера, подмена «лежащего» сайта-источника.

## 10. ADR (принятые решения)

Каждый ADR содержит строку «В продакшене я бы...».

| ADR | Решение | В продакшене я бы... |
| --- | --- | --- |
| 001 | Развитие от боли: начинаем с монолита и воркера | Начинал бы с монолита и добавлял слои (кэш, отдельные сервисы, оптимизации) по мере роста системы и нагрузки, исходя из замеров. |
| 002 | Обучение важнее продукта | Наоборот: выбирал бы самое простое и оптимальное решение с минимальными затратами. |
| 003 | Брокер RabbitMQ | BullMQ: встроенные повторы и аренда, проще поддержка, 14 RPS хватает. |
| 004 | Postgres + OpenSearch с outbox | Postgres FTS: на один компонент меньше, нет синхронизации. |
| 005 | Идентичность страницы — предварительный адрес после нормализации. Таблица «вариант адреса → страница» с уникальностью варианта на уровне базы. | Так же. |
| 006 | Текст страницы от расширения не принимаем, чтобы в общее содержимое не попали закрытые данные пользователей и поддельный текст. | Так же. |
| 007 | Консервативная нормализация адреса: ошибаемся в сторону дубликатов, а не склейки разных страниц. | Так же. |
| 008 | Повторы 1/5/30/360 мин, 4 попытки. Цифры выбраны императивно. | Исходил бы из задачи и провёл предварительную аналитику, чтобы выбрать паузы и число попыток. |
| 009 | Задача берётся воркером в аренду с меткой времени. Если воркер упал, задача возвращается из аренды и её подхватывает другой воркер. Одновременная обработка исключается атомарной вставкой записи «обрабатывается». | Так же. |

## 11. Открытые вопросы

- Способ фильтра «только мои страницы» в поиске: выбрать замером.
- Стратегия обновления известных страниц.
- Связь автокатегории (общая) и дерева папок (личное): как предложение папки сопоставляется с папками пользователя.
- Хранить ли оригинальный текст страницы или только индекс.
- Способ усиления доверия к `userId` внутри сети.
- Поддержка Web Share Target на iOS.

## 12. Риски

- Затягивание по времени при 4-5 часах в неделю.
- Потеря мотивации из-за долгих этапов без видимого продукта: поэтому этап 1 даёт рабочий скелет, а этап 4 — первую ощутимую пользу.
- Раздувание объёма этапа. Мера: этап закрывается по критериям готовности, новые идеи уходят в список открытых вопросов.
- Учебные решения вместо продуктовых могут вводить в заблуждение о пригодности технологий. Мера: строка «в продакшене я бы...» в каждом ADR.

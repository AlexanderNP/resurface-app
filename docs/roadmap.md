Правила:

- Текущий этап — первый, в котором не все пункты отмечены. Один этап — один чат.
- Пункт отмечается выполненным только после проверки (тесты, линтер, замер) и подтверждения автора.
- 🎓 — место, где сначала думает и приносит черновик автор, затем идёт ревью. Готового ответа в пункте нет намеренно.
- Чек-лист следующего этапа составляется в начале его чата, после изучения темы.

## Этап 1. Скелет

### Контекст

Цель этапа — работающий API без воркера и очередей: сохранить URL, получить одну общую страницу на все варианты одного адреса, разложить сохранения по личному дереву папок. Всё покрыто тестами на настоящем Postgres, запускается одной командой и проверяется в CI.

Тема: System Design Primer, раздел Application layer. Что из неё применяется:

| Понятие из темы | Где применяется в этапе |
| --- | --- |
| Отделение слоя приложения, границы ответственности | Модули Nest с явными границами (блок D, E); ADR 001 |
| Цена микросервисов | Сохранение URL как одна транзакция в одной базе (пункт 4.3); ADR 001 |
| Сервис без состояния | Конфигурация из окружения (1.3), личность пользователя из заголовка (4.2), проверка на двух экземплярах (6.4) |

Оценка объёма: 6-8 недель при 4-5 часах в неделю. Это оценка ассистента, не замер.

| Решение | ADR |
| --- | --- |

| Личность пользователя: заголовок `X-User-Id` и guard | [012](adr/012-lichnost-polzovatelya-zagolovok.md) |

### Чек-лист

#### A. Каркас

- [x] 1.0 — Тема Application layer прочитана, понимание проверено (готово, когда: три вопроса разобраны в чате этапа).
- [ ] 1.1 — Создать проект Nest.js с TypeScript в строгом режиме, линтером и форматтером (готово, когда: `lint`, `build` и `test` проходят на пустом проекте одной командой каждая).
- [ ] 1.2 — Docker Compose с Postgres для разработки (готово, когда: `docker compose up -d` поднимает базу, данные переживают перезапуск контейнера, параметры подключения берутся из переменных окружения).
- [ ] 1.3 — Конфигурация приложения из переменных окружения с проверкой при старте (готово, когда: без обязательной переменной приложение не стартует и пишет, какой именно не хватает; в репозитории есть `.env.example`, а `.env` в `.gitignore`).
- [ ] 1.4 🎓 — Модуль базы данных: подключить Drizzle к Nest. Выбери способ: официальный `@nestjs/drizzle` (версия `0.0.1`) или свой провайдер; факты для выбора в ADR 010. Прочитай в документации Nest раздел Custom providers. Подумай: кто создаёт пул соединений, кто его закрывает при остановке приложения и что будет с незавершёнными запросами, если не закрывать (готово, когда: `GET /health` выполняет запрос к базе и отвечает 200; при остановленной базе отвечает ошибкой, а не зависает; при остановке приложения пул закрывается).
- [ ] 1.5 — Миграции: команды для генерации и применения (готово, когда: на пустой базе одна команда создаёт схему, повторный запуск ничего не меняет, файлы миграций лежат в git).

#### B. Схема данных и идентичность страницы

- [ ] 2.1 🎓 — Черновик схемы таблиц: пользователи, страницы, варианты адреса, сохранения, папки. Формат: таблица или список «колонка, тип, ограничения» в чате, без кода. Опирайся на requirements, раздел 4. Подумай над вопросами: что является первичным ключом таблицы вариантов; какое ограничение не даст одному пользователю сохранить одну страницу дважды; «Входящие» — это строка в таблице папок или отсутствие папки; что происходит с сохранениями и вложенными папками при удалении папки; могут ли две папки с одним именем лежать рядом (готово, когда: черновик прошёл ревью, создан ADR 005).
- [ ] 2.2 — Описать схему в Drizzle и сгенерировать первую миграцию (готово, когда: миграция применена, в базе видны все уникальные ограничения и внешние ключи из черновика).
- [ ] 2.3 — Тестовые пользователи (готово, когда: одна команда создаёт в базе двух пользователей с известными идентификаторами; повторный запуск не создаёт дубликатов).
- [ ] 2.4 🎓 — Окружение интеграционных тестов на настоящем Postgres. Выбери, откуда берётся база (контейнер из теста или сервис Compose) и как тесты изолированы друг от друга. Подумай: что будет, если два теста пишут в одну таблицу и запускаются параллельно; чем очистка таблиц отличается от отката транзакции и какие проверки этапа (см. 4.4) откат транзакции сделает невозможными (готово, когда: один пример теста пишет в базу и читает из неё; набор тестов проходит три раза подряд с одинаковым результатом).

#### C. Нормализация адреса

- [ ] 3.1 🎓 — До кода: таблица примеров «адрес на входе → адрес на выходе», не меньше 20 строк. Обязательно покрыть каждое правило из requirements, раздел 4, и случаи, которые там не решены: завершающий слэш, фрагмент (`#...`), порт по умолчанию, порядок параметров, пустая строка параметров, домен в верхнем регистре, кириллический домен, схемы не `http`/`https`, строка, которая не является адресом. Каждый нерешённый случай реши сам по принципу «ошибаться в сторону дубликата, а не склейки» и запиши одной фразой почему (готово, когда: таблица прошла ревью, решения записаны в ADR 007).
- [ ] 3.2 🎓 — Функция нормализации и unit-тесты по таблице из 3.1. Подумай: почему эта функция не должна зависеть ни от Nest, ни от базы; что должно получиться, если нормализовать уже нормализованный адрес, и как это проверить одним тестом на всей таблице (готово, когда: каждая строка таблицы — отдельный тестовый случай, все проходят; есть тест на повторную нормализацию; модуль не импортирует ничего из Nest и слоя базы).
- [ ] 3.3 — Недопустимый адрес даёт понятную ошибку (готово, когда: для строки-не-адреса и для неподдерживаемой схемы функция возвращает ошибку определённого вида, по которой вызывающий код отличает «плохой ввод» от сбоя; есть тесты).

#### D. Сохранение URL

- [ ] 4.1 🎓 — Черновик контракта эндпоинтов этапа: сохранения (создать, список) и папки (создать, переименовать, переместить, удалить, получить дерево, положить сохранение в папку). Формат: метод, путь, тело запроса, тело ответа, коды ответа. Подумай: что вернуть, когда пользователь второй раз сохраняет тот же адрес, и почему клиенту (расширению с ненадёжной сетью) важен именно такой ответ; какие поля ответа понадобятся расширению на этапе 4 (готово, когда: черновик прошёл ревью, контракт записан в `docs/api.md`).
- [ ] 4.2 — Guard для `X-User-Id` и декоратор параметра с текущим пользователем (готово, когда: без заголовка и с заголовком неверного формата ответ 401; контроллеры получают пользователя только через декоратор; есть тесты).
- [ ] 4.3 — Проверка входных данных эндпоинтов (готово, когда: запрос с неверным телом получает 400 с указанием поля; недопустимый адрес из 3.3 тоже даёт 400, а не 500).
- [ ] 4.4 🎓 — Сценарий «сохранить URL»: нормализовать, найти или создать страницу через таблицу вариантов, создать сохранение. Подумай: два запроса с одним новым адресом приходят одновременно — что видит каждый между «проверил, что страницы нет» и «вставил»; кто должен быть судьёй, код или база; где проходят границы транзакции и что останется в базе, если упасть посередине. Подсказка-направление: `INSERT ... ON CONFLICT` в документации Postgres (готово, когда: интеграционные тесты проходят: первое сохранение создаёт страницу, вариант и сохранение; сохранение того же адреса с другими `utm_*` вторым пользователем даёт ту же страницу и второе сохранение; новое сохранение попадает во «Входящие»).
- [ ] 4.5 — Тест на гонку: 20 одновременных сохранений одного нового адреса разными пользователями (готово, когда: в базе ровно одна страница, один вариант адреса и 20 сохранений, ни одного ответа 5xx; тест проходит 10 запусков подряд; результат записан в ADR 005 как факт).
- [ ] 4.6 — Повторное сохранение того же адреса тем же пользователем (готово, когда: дубликат не создаётся, ответ соответствует контракту из 4.1; есть тест, в том числе на два одновременных запроса).
- [ ] 4.7 — Список сохранений пользователя с пагинацией и сортировкой по дате (готово, когда: пользователь A не видит сохранения пользователя B; порядок стабилен при одинаковой дате; есть тесты).

#### E. Дерево папок

- [ ] 5.1 — Создание и переименование папки (готово, когда: папка создаётся в корне и внутри другой; нельзя создать папку внутри чужой; правило про одинаковые имена из 2.1 проверено тестом).
- [ ] 5.2 🎓 — Получение дерева. Два пути: рекурсивный запрос в Postgres или выборка всех папок пользователя и сборка дерева в коде. Выбери и обоснуй одной фразой. Подумай: что из этого проще при сотнях папок и какое число нужно замерить, чтобы пересмотреть выбор (готово, когда: эндпоинт возвращает дерево; тест на три уровня вложенности проходит; выбор и причина дописаны в ADR 011).
- [ ] 5.3 🎓 — Перемещение папки. Подумай: как одним запросом узнать, что новая родительская папка не лежит внутри перемещаемой; что случится, если одновременно переместить A в B и B в A, и достаточно ли для этого проверки в коде (готово, когда: тесты проходят: обычное перемещение; в саму себя — отказ; в собственную вложенную — отказ; в чужую папку — отказ; ответ на вопрос про одновременные перемещения записан в ADR 011, даже если решение — «принимаем риск»).
- [ ] 5.4 — Удаление папки (готово, когда: поведение для вложенных папок и сохранений соответствует решению из 2.1 и проверено тестами).
- [ ] 5.5 — Перемещение сохранения в папку и обратно во «Входящие» (готово, когда: нельзя положить сохранение в чужую папку; есть тесты).

### Критерии готовности этапа

1. Все пункты чек-листа отмечены.
2. `docker compose up` на чистой копии репозитория даёт работающий API.
3. CI зелёный: линтер, unit- и интеграционные тесты на настоящем Postgres, сборка образа.
4. Есть факты из проверок: тест на гонку (4.5) и проверка двух экземпляров (6.4), оба записаны в ADR.
5. ADR 001, 005, 007, 010, 011, 012 оформлены полностью, решения сверены с источником.

### Риски и открытые вопросы

- **Раздувание объёма.** В этапе нет воркера, состояний обработки страницы, поиска, аутентификации и интерфейса. Идеи вне списка уходят в requirements, раздел 11.
- **Состояние обработки страницы.** На этапе 1 у страницы нет колонки состояния: её форма (взаимоисключающие состояния) проектируется на этапе 2. Миграция на этапе 2 добавит её к существующим строкам.
- **`rel=canonical`.** Чтение тега возможно только после похода за страницей (этап 2). На этапе 1 таблица вариантов хранит только предварительные адреса, но её форма должна допускать второй вариант для той же страницы.
- **Зрелость `@nestjs/drizzle`.** Версия `0.0.1` от 23.09.2026; запасной путь — свой провайдер (ADR 010).
- **Одновременные перемещения папок** могут создать цикл в обход проверки в коде. Решение принимается в пункте 5.3.
- **Нагрузочных замеров в этапе нет:** они относятся к этапу 5. Числа этапа 1 — это результаты тестов на корректность, а не на производительность.

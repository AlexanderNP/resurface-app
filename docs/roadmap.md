# План по этапам

Документ — источник правды о статусе проекта. Перечень этапов и тем для чтения: [requirements.md](requirements.md), раздел 9. Решения: [adr/](adr/). Термины: [glossary.md](glossary.md).

Правила:

- Текущий этап — первый, в котором не все пункты отмечены. Один этап — один чат.
- Пункт отмечается выполненным только после проверки (тесты, линтер, замер) и подтверждения автора.
- 🎓 — пункт System Design: автор приносит черновик артефактом (код, контракт, диаграмма, таблица), затем идёт ревью. Строка «Черновик покрывает» — что в нём должно быть видно; письменных ответов не нужно.
- Пункт без 🎓 — инструментальный: ассистент даёт пример из документации и шаги, вопросов нет (CLAUDE.md, «Два вида пунктов»).
- Чек-лист следующего этапа составляется в начале его чата, после изучения темы.
- Сначала ядро этапа. Доработки инструментов (линтер, строгость типов, чистка конфигурации) в чек-лист не попадают, а записываются в [tech-debt.md](tech-debt.md) и делаются после ключевых этапов.

## Этап 1. Скелет

### Контекст

Цель этапа — работающий API без воркера и очередей: сохранить URL, получить одну общую страницу на все варианты одного адреса, разложить сохранения по личному дереву папок. Всё покрыто тестами на настоящем Postgres, запускается одной командой и проверяется в CI.

Тема: System Design Primer, раздел Application layer. Что из неё применяется:

| Понятие из темы | Где применяется в этапе |
| --- | --- |
| Отделение слоя приложения, границы ответственности | Модули Nest с явными границами (блок D, E); ADR 001 |
| Цена микросервисов | Сохранение URL как одна транзакция в одной базе (пункт 4.3); ADR 001 |
| Сервис без состояния | Конфигурация из окружения (1.3), личность пользователя из заголовка (4.2), проверка на двух экземплярах (6.4) |

Оценка объёма: 6-8 недель при 4-5 часах в неделю. Это оценка ассистента, не замер.

#### C. Нормализация адреса

- [ ] 3.1 🎓 — До кода: таблица примеров «адрес на входе → адрес на выходе», не меньше 20 строк. Обязательно покрыть каждое правило из requirements, раздел 4, и случаи, которые там не решены: завершающий слэш, фрагмент (`#...`), порт по умолчанию, порядок параметров, пустая строка параметров, домен в верхнем регистре, кириллический домен, схемы не `http`/`https`, строка, которая не является адресом. Нерешённые случаи решаются по принципу «ошибаться в сторону дубликата, а не склейки»; причина — колонка таблицы (готово, когда: таблица прошла ревью, решения записаны в ADR 007).
- [ ] 3.2 🎓 — Функция нормализации и unit-тесты по таблице из 3.1. Код покрывает: функция без зависимостей от Nest и базы (чистая функция); идемпотентность — повторная нормализация не меняет результат, проверка одним тестом на всей таблице (готово, когда: каждая строка таблицы — отдельный тестовый случай, все проходят; есть тест на повторную нормализацию; модуль не импортирует ничего из Nest и слоя базы).
- [ ] 3.3 — Недопустимый адрес даёт понятную ошибку (готово, когда: для строки-не-адреса и для неподдерживаемой схемы функция возвращает ошибку определённого вида, по которой вызывающий код отличает «плохой ввод» от сбоя; есть тесты).

### Ревью схемы, итерация 1

Первая версия схемы: [db_schema.jpg](db_schema.jpg). Верно: `url` как первичный ключ вариантов адреса, составной ключ `(user_id, page_id)` у сохранений, `parent_id` с `NULL` у корневых папок. Замечания, на которые должна ответить вторая версия:

1. **`folders__user_pages`** делает связь «многие ко многим» (в требованиях папка у сохранения одна) и смешивает размещение с предложениями системы (`source`, `score`), которые на этапе 1 нечем заполнить. Не гарантировано, что папка принадлежит тому же пользователю. Направление: одна папка на сохранение, отсутствие папки — «Входящие»; предложения — отдельная таблица на своём этапе. Несколько папок — продуктовое решение, требует правки requirements.
2. **`folders.path`** — материализованный путь поверх списка смежности, второй источник правды; противоречит ADR 011.
3. **Колонки не из этапа 1:** `pages.status` (значения не совпадают с requirements, раздел 5), `pages.title`, `keywords`, `auto_category`, `fetched_at`, `is_public`, `user_pages.visibility`, `user_pages.tags`, `folders.auto_category`. Колонка появляется вместе с кодом, который её пишет.
4. **`pages.canonical_url`** дублирует вариант с `kind = 'canonical'`. У `pages` нет ни одной уникальной колонки: возможна страница без варианта (связано с пунктом 4.4).
5. **Ограничения папок:** не решено, могут ли одноимённые папки лежать рядом (учесть поведение `NULL` в уникальном ограничении, см. `NULLS NOT DISTINCT`); внешний ключ `parent_id` не мешает положить папку в чужую.
6. **`NOT NULL` и удаление:** `NOT NULL` указан только у `created_at`; для каждого внешнего ключа не указано, что происходит при удалении родителя.
7. **Длина `url`:** значение длиннее примерно 2700 байт не поместится в индекс и даст ошибку базы; нужен предел на входе и строка в таблице примеров пункта 3.1.
8. Мелочи: `generated always as identity` вместо `bigserial`; одной фразой объяснить в ADR 005, почему у страниц `bigint`, а у пользователей и папок `uuid`.

### Критерии готовности этапа

1. Все пункты чек-листа отмечены.
2. `docker compose up` на чистой копии репозитория даёт работающий API.
3. CI зелёный: линтер, unit- и интеграционные тесты на настоящем Postgres, сборка образа.
4. Есть факты из проверок: тест на гонку (4.5) и проверка двух экземпляров (6.4), оба записаны в ADR.
5. ADR 001, 005, 007, 010, 011, 012, 013 оформлены полностью, решения сверены с источником.

### Риски и открытые вопросы

- **Раздувание объёма.** В этапе нет воркера, состояний обработки страницы, поиска, аутентификации и интерфейса. Идеи вне списка уходят в requirements, раздел 11.
- **Состояние обработки страницы.** На этапе 1 у страницы нет колонки состояния: её форма (взаимоисключающие состояния) проектируется на этапе 2. Миграция на этапе 2 добавит её к существующим строкам.
- **`rel=canonical`.** Чтение тега возможно только после похода за страницей (этап 2). На этапе 1 таблица вариантов хранит только предварительные адреса, но её форма должна допускать второй вариант для той же страницы.
- **Drizzle ветки `rc`.** API может меняться до выхода `1.0`; обновления — отдельной задачей с проверкой сборки и тестов (ADR 010).
- **Одновременные перемещения папок** могут создать цикл в обход проверки в коде. Решение принимается в пункте 5.3.
- **Нагрузочных замеров в этапе нет:** они относятся к этапу 5. Числа этапа 1 — это результаты тестов на корректность, а не на производительность.
